# Program board

A one-page view of a coordinated program for the browser canvas. It answers
"what is running, what is done, and what did it cost" without a second state
store.

```text
python3 ~/.copilot/installed-plugins/architrave/architrave/harness/program_board.py --watch 120 --reqs REQ-53,REQ-54,REQ-55
```

Replace the example IDs with this session's requirements. Scope is mandatory:
`--reqs` selects the session view; `--all-reqs` deliberately shows the entire
repository ledger, including historical work. Neither is inferred from ledger
status: previously accepted requirements need not belong to this session.
Unknown IDs fail without replacing the board. The scope is printed above the
overview and retained on refresh and in the stopped snapshot. Historical rows
remain in `SPEC.md`; they are not copied or deleted to create a session view.

Start it once per coordinator in a background (detached) shell; a second start
exits because a watcher already holds `<output>.pid`. Use the plugin's actual
install path on other hosts.

Run it from the folder holding the requirements file (or pass `--ledger`). The
coordinator session defaults to `COPILOT_AGENT_SESSION_ID` and the output to that
session's `files/program-board.html`; open it in the browser canvas. With
`--watch` it rewrites the file every 120 seconds, the page reloads itself, and
the watcher exits after the program has been quiet for two hours. The lead
starts it for every non-trivial task. A watcher registers itself in the
coordinator session's `files/program-board.watch` (pid, output, ledger,
interval, selected REQ IDs). While lanes are running, `requirements` prints a
start command scoped to the running lanes' REQs when the coordinator has no live
board covering them for that ledger. Legacy unscoped registrations and boards
missing those REQs do not satisfy the reminder. The
coordinator is a session named in no lane row whose own log created (a
session-creating tool call) or messaged a running lane's session; lanes,
reviewers and other sessions are not reminded, and neither is a coordinator
that records its own session in a lane row for direct work. Live means the pid exists and the output
was rewritten within two intervals plus a minute. A session keeps one
registration, so a coordinator watching two ledgers is reminded about one. A killed watcher
leaves a stale pointer, which the next watcher replaces. It is a reminder,
never a failure. After a coordinator rotates, start the board under the
successor.

## What it shows

| Section | Source |
|---|---|
| Overview: selected accepted REQs and worker lanes, repository-wide structural checks, cumulative history sessions/tokens/minutes | Working-tree requirements file and local session logs |
| Lanes: one rectangle per lane, one square per REQ (green accepted, green hatching delivered by a done lane but not yet accepted, blue claimed, red blocked, grey open); select a square for its requirement | `## GHC Scheduler` lane table and REQ rows |
| How the sessions ran: per session a time bar (first to last event, dark marks for model turns), agent, model/wall minutes, live state, a current-context gauge (latest prompt size) against the model limit and a token gauge | `~/.copilot/session-state/<id>/events.jsonl` of the coordinator and the child sessions it created with `create_session` |

It is dense by design and fits a narrow side panel; there are no tables. Synthetic
"Requirements"/"Not in a lane" groups are not workers and do not enter the worker
lane denominator. Session scope filters REQ counts, lane membership and
review/evidence diagnostics. Structural checks still cover the whole repository
ledger and are labelled accordingly; a scoped view does not prove repository
completion. Recursive history can span several tasks in one coordinator;
its costs are not a current-task estimate. Full session names and exact values
follow the compact chart and remain available in print.

## Completion

A session whose last action was the host's "Task completed" (no model turn after it) shows a green bar and "task completed", even if its lane row is not yet updated. A later turn makes it active again.

Every board identifies generated bytes by timestamp and ledger digest, separately
from the page-load observation and a print/export request. A later file rewrite
does not update an already observed page until it reloads. The printed page
retains its snapshot identity; the print event does not prove that an export
completed. Session-log cutoff and the coordinator's observed terminal status
are separate: before its completion event, the board says **pre-completion
projection**, not completed live state.

After the last ledger correction, regenerate, then reload/read the consumer
before claiming the displayed page reflects it. Use a one-shot static handoff
or a bounded final observation; do not keep a watcher running indefinitely just
to capture the coordinator's future completion. One-shot output is labelled
static. A watcher that exits normally or receives SIGTERM/SIGINT regenerates
a stopped/static snapshot and removes its live registration. Forced termination
may retain older auto-refresh bytes; an auto-refresh request is not a liveness
guarantee. Sidecars (`.pid`, `.watch`, `.rotate.json`) alone never establish live
workers; check the process and output freshness as described above.

## Context flags

Context is the latest prompt size, not the peak, judged against the session's
first prompt (its system prompt and tools), even when earlier events are
clipped. "context high" (≥30% of the limit or ≥300k, with 1.5× the first prompt
or a quarter of the remaining room used) is information; "rotate at next task
boundary" with a gold ↻ (≥45%, with 2× the first prompt or half the remaining
room used) is listed in `<output>.rotate.json` with the time it was first
flagged. A fresh session on a small-window model is never flagged. Rotation steps and evidence are in
`knowledge/execution-policy.md` (Context rotation).

## Review marks

- Session row: grey ✓ when the session ran a reviewer agent (adversarial judge, code review, rubber duck, security review or `architrave-review`); ○ when none. It shows that a review ran, not its verdict.
- Square: a corner when the REQ's latest `review: <reviewer> <verdict>` note (at the start of the cell or after `;` or `,`) is PASS — white when the note names a reviewer session whose local log shows a reviewer role ending in PASS, grey when the note can't be checked. Findings verifiers do not count. The overview shows how many PASS reviews are verified.
- Lane: "reviewed k/n"; a gold border and "review missing" when a `done` lane has any open REQ, or any lane has an accepted REQ, without a PASS review (withdrawn and superseded REQs are skipped). This is the same rule `requirements --done` enforces for ledger lanes; the "Not in a lane" box only gets the gold border for accepted, unreviewed REQs.
- Review notes attach to REQs, not lanes: one PASS on a REQ covers every lane that lists it. The overview counts accepted but unreviewed REQs.
- The `requirements` gate parses every note, requires the latest to be PASS for an accepted REQ, and rejects a reviewer named like the REQ's owner. A note naming a full session UUID is checked against `session-state/<uuid>/events.jsonl`: the kickoff agent (selected before the first turn) must be a reviewer role, and the ruling of the session's last report (its `task_complete` summary or a message it sent another session) must match. A ruling is the first labelled line (`Verdict: REVISE`, `Re-review of X: PASS`), else the first line opening with an upper-case verdict (`**PASS** on …`); quoted, backticked, `>` and table text and mid-sentence verdict words never count, so reviewers should start their report with a `Verdict:` line. Earlier notes naming the same session (a re-review) need only match one of its reports. A contradiction fails the gate. Use a fresh reviewer session for each delivery: a reused session's later ruling contradicts the earlier note.
- Where local session logs exist (the Copilot app and CLI), `requirements --done` and the board's "review missing" count only verified PASS notes, so role names and sessions from other machines do not close a lane. On hosts without those logs every note is unverified and accepted as written. A reviewer that ran elsewhere (a cloud, Claude or Codex session) cannot close a lane on a machine that has logs; run the review as a local visible session. With `review.crossFamily`, every model the lane and the reviewer sessions used (start and mid-session switches) must be logged, not `auto`, and share no family, otherwise the lane shows a gap.
- This catches mistakes and stale claims, not deliberate forgery: an agent that can write files can fake a log.

## Checks and limits

- The overview labels **ledger structural checks**, not a generic gate PASS. It
  preserves all errors, source-verification notes and open serious findings.
  Completion acceptance is not evaluated by the board. With a configuration,
  use `requirements --done` for completion; without one, the board explicitly
  labels plugin-only structural scope and unavailable completion checks. The
  standalone CLI's configuration-discovery prerequisite is unchanged. Do not
  create configuration or force adoption just to clear a board.
- A gold ring marks an accepted REQ whose identity evidence is missing,
  incomplete, unsupported, changed or unreadable; the evidence list explains
  which. Legacy commit evidence still recognizes existence in the ledger or
  configured components, not entailment or artifact identity. See below for
  intentionally uncommitted artifacts.
- Lane sessions not logged on this machine get a dashed row without metrics.
- Tokens are split into new input, cached reads and output. Sessions that began before the coordinator count only from its start.
- REQs in no lane appear in a "Not in a lane" rectangle (or one "Requirements" rectangle without a lane table).
- Child sessions created by `create_session`, `open_pr_session`, `open_issue_session` or `fork_session` are followed recursively.
- New input = prompt tokens minus cache reads (cache writes count as new). A malformed log line is skipped; a failed refresh keeps the last good board.
- Logs are read incrementally (only new bytes each refresh); requirement text is copied into the board file in the session folder.
- Rotation's benefit is not measured yet; thresholds are a published-evidence heuristic, not tuned for coding.
- It reads files only: no ledger, session or repository changes and no network requests.
- Browser-canvas screenshots can return stale frames (a host issue); verify with the page contents or a fresh render.
- Repository HEAD is labelled separately from the working-tree ledger actually
  read, its clean/modified/untracked status and SHA256 of those exact bytes.
  All history timestamps use UTC with dates.
- Print uses wrapped full names and exact values rather than the compact SVG,
  keeps headings with content and removes interactive-only instructions.
  Interactive keyboard/readability claims must be checked separately from PDF.

## Artifact identity evidence

An evidence cell can explicitly identify a local file, without committing it:

```text
artifact: {"path":"reports/design.md","sha256":"<64 hex digits>","reviewed_sha256":"<same 64 hex digits>"}; review: <reviewer-session-uuid> PASS
```

`path` is relative to the ledger directory or an absolute local path. Multiple
`artifact:` JSON objects are allowed; every claimed file must match. A path
without a valid digest is incomplete; malformed metadata and bare digests
without a locator are unsupported. Missing files, unreadable files and changed
content remain distinct. Appending an unrelated resolving commit cannot
rescue any artifact claim, including malformed metadata.

`sha256` verifies only the bytes read at refresh. `reviewed_sha256` explicitly
declares which bytes the REQ's review covered; it must match the current digest
and have a PASS review note. Missing or mismatched bindings are shown even when
file identity matches. Session verification separately reports whether the
reviewer role/verdict is logged; it does not prove substantive review quality.
These are author-supplied bindings, not authenticated reviewer attestations.
No new evidence framework or requirement for old rows to contain this metadata
is implied. Preserve unsupported historical evidence as such, rather than
turning every warning green.

Record the actual review passage and scope in final Evidence rows: structural
checks, semantic sampling and retained-but-unverified sources are not equivalent.
Reviewer placeholders such as `pending` cannot support evidence; a populated
name or UUID alone is not exhaustive source verification. File identity,
semantic review and behavioral/owner acceptance remain separate.

For reproducible synthetic print and interaction checks, with existing
Playwright Chromium and `pypdf` available:

```text
python3 scripts/test-program-board.py --browser-output <session-artifact-directory>
```

The optional browser case exports a real multi-page PDF, checks complete names
and exact values, heading pagination, all six errors, saved-versus-observed
state, post-snapshot completion and Enter/Space activation independently. It
does not certify every browser, screen reader or private research artifact.
